# Spec: P0 灰盒原型验证

Status: ready-for-agent
来源：issues/01–08 的「待原型验证」汇总；路线图见 issues/08-scaling-roadmap.md
词汇表：GLOSSARY.md　相关 ADR：0001–0005

## Problem Statement

项目处于规划完成、代码为零的阶段。01–07 号研究产出了 9 项「纸面假设」——同屏性能、加载耗时、工具链行为等关键数字全部未经实测。不验证这些假设，P1 垂直切片的规格无法写，07 的性能预算是空谈。

## Solution

P0 灰盒原型：一个最小 Babylon 灰盒场景 + 一个统一的验证 Harness，把 9 项假设变成 9 个可执行、可量化、有验收阈值的场景。产出实测报告，修正预算，决定 3 个降级预案是否触发。

## User Stories

1. 作为开发者，我想要一个统一 Harness 跑所有验证场景，使 9 项验证有一致的环境与报告格式
2. 作为开发者，我想实测 300 骨骼动画角色在正交相机下的帧率，以确定角色预算
3. 作为开发者，我想对比 WebGL2 与 WebGPU 路径的帧率，以确认增强路径的真实收益
4. 作为开发者，我想实测 Crowd V2 在 200×200 区域的 navmesh 生成时间与内存，以确定区域规模上限
5. 作为开发者，我想验证跨区域 navmesh 热替换的平滑性，以确认加载门方案无断点
6. 作为开发者，我想实测 HighlightLayer 在多角色遮挡下的开销，以确定描边方案的可用性
7. 作为开发者，我想实测 50MB glTF 的 AssetContainer 加载耗时与内存峰值，以验证单区域预算
8. 作为开发者，我想确认 Babylon Editor 项目文件的 git 友好度，以决定是否触发 LDtk 降级
9. 作为开发者，我想实测 meshopt vs draco 的解码速度与压缩率，以锁定几何压缩方案
10. 作为开发者，我想实测自动 LOD 的视觉质量，以决定角色 LOD 级数
11. 作为开发者，我想确认 KTX2 在 Safari/WebGPU 下的转码兼容性，以锁定纹理方案
12. 作为开发者，我想验证 headless Blender 导出脚本的可重复性，以确认管线可进 CI
13. 作为开发者，我想实测 inkjs 处理几百节点对话树的性能与变量存档快照，以确认对话方案可行
14. 作为开发者，我想用修饰器模型原型装备/buff/任务奖励三场景，以验证 schema 表达力后冻结
15. 作为开发者，我想验证 ego-browser 驱动 Harness 的冒烟稳定性，以确认 L4 测试可行
16. 作为开发者，我想确认 vitest 直测逻辑类的边界，以巩固逻辑/表现分离
17. 作为项目所有者，我想收到一份结构化 P0 报告（每项：数字 vs 阈值 vs 结论），以修正 07 预算并决策 P1
18. 作为开发者，我想验证 VRoid 角色 → Blender → glTF → Babylon toon 渲染的完整链路（一个角色 + 一段 Mixamo 动画 + toon 开关），以确认二次元美术方案在 P1 前走通

## Implementation Decisions

- 新建 src/logic/（修饰器模型、inkjs 封装、存档迁移链雏形）与 src/render/（灰盒 Harness 场景）——逻辑/表现分离从第一天强制（ADR-0005）。
- 单一 seam：P0Harness——每个验证场景是 Harness 的一个具名 scenario，输出统一 JSON 测量报告（场景名、指标、数值、环境信息）。
- 渲染类场景（性能/加载）由 ego-browser 驱动采集；逻辑类场景直接 vitest。
- 灰盒资产：程序化几何体 + 占位贴图。例外：验证项 18 允许一个 VRoid 角色 + 一段 Mixamo 动画（09 号方案的最小验证集），严格不扩展为美术工作（不做角色变体/场景资产）。
- 降级预案预注册：Editor git 不友好 → LDtk；inkjs 不可用 → 自研极简对话 DSL；KTX2 Safari 失败 → PNG 回退。
- 验收阈值来自 07 预算草案（60fps/30fps、≤50MB 区域、draw calls ≤300 等），P0 产出用于修正它们。
- 版本锁定：Babylon 9.x 精确版本 + recast-navigation-js 版本在项目初始化时锁定（ADR-0001）。

## Testing Decisions

- 每个验证场景的测试就是场景本身：可重复执行、输出确定性数字。
- 逻辑类（修饰器、存档迁移）按 L1 标准：只测外部行为（给定输入状态 → 期望输出状态），不测实现细节。
- ego-browser 冒烟（验证项 15）允许 flaky 重试，不阻塞其他验证。
- Harness 报告格式为后续 L5 夜测复用。

## Out of Scope

- 任何正式美术资产（09 号 ticket 负责）。
- 玩法设计（题材/战斗/核心循环——与 P0 并行补充）。
- 存档迁移链完整实现（只做雏形验证可序列化）。
- 多章节内容、对话完整树、任务系统全量。
- CI 部署（本地验证为先，CI 集成在 P1）。

## Further Notes

- 九项验证完成后：修正 07 预算、更新受影响 ADR（0002/0003/0004 的代价节）、然后进入 P1 规格。
- 灰盒 Harness 的场景注册机制为 P1 场景管理打基础，但不预做抽象。
